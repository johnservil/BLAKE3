# Working on BLAKE3 servil

This fork of BLAKE3 1.8.7, published as the crate `blake3-servil`, aims
at the fastest BLAKE3 in every situation a program meets: alone, beside
other work, beside other hashing threads, natively and in virtual
machines. This file holds what you need to change it and to cooperate
with its maintainers. Questions about BLAKE3 itself, or about the
official crate, belong upstream at
[BLAKE3-team/BLAKE3](https://github.com/BLAKE3-team/BLAKE3).

## Where things are

The README lists what the fork adds for callers; the code is laid out so:

- `c/`: the assembly kernels the crate builds. On AArch64, the integer +
  NEON hybrids (`blake3_neon_hybrid_aarch64.S`, generated by
  `tools/gen_neon_hybrid.py`) and the SME2 kernels; on x86-64, upstream's
  SSE4.1, AVX2, and AVX-512 kernels. The fork's own x86-64 kernels, in
  Rust intrinsics, are in `src/rust_sse41.rs` and `src/rust_avx2.rs`.
- `src/`: the Rust around them. `lib.rs` (the one-shot calls, the
  `Hasher`), `platform.rs` (detection and dispatch), `many.rs` (batches),
  `each.rs` (collections, `update_each`), `lanes.rs` (the thread pool),
  `queue.rs`, `outboard.rs` (outboards and the `Verifier`),
  `self_test.rs` (the startup self-test), `hasher.rs` (the Hasher's
  stack, loop, and chunk state), and `tree.rs` (the tree walk).
- `capi/`: the C API, `b3.h`, a thin layer over the crate
  (`capi/src/lib.rs`), tested from Rust against the official test vectors
  and from C (`capi/tests/`).
- `tools/verify/`: the proofs (QUALITY.md, "Proofs"); `tools/mutants/`:
  mutation testing and the list of mutants known to survive.

`NOTES-servil.md` holds the design and the measurements behind it,
including the ideas tried and rejected.

## Build and test

The supported C compilers are those of supported operating systems: GCC
12 or later (Debian 12's, the oldest; CI builds and tests with it), Clang,
and MSVC as current releases ship them; official BLAKE3 serves older ones.

On AArch64 Linux and macOS the build includes the SME2 kernel when the C
compiler assembles SME2: Clang 17 or later (Xcode 15 or later), or GCC 14
or later with binutils 2.41. With an older compiler it builds without the
kernel and warns (`CC=clang-19 cargo build` adds it on Debian 12, for
example). The `no_sme2` feature leaves the kernel out on purpose. On a
CPU with SME2, `perf_regress` stops when the build lacks the kernel.

```sh
cargo test --release --lib --tests
cargo test --release --lib --tests --features no_sme2
cargo test --release --lib --tests --features pure
cargo test --release --doc
cargo test --release --manifest-path test_vectors/Cargo.toml
cargo test --release --manifest-path capi/Cargo.toml   # the C API
sh tools/check-builds.sh            # the builds the suites leave out
pypy3 tools/mutants/check.py        # about an hour: every surviving mutant known
```

A change that makes a mutant survive, or lets a listed one be caught,
fails `tools/mutants/check.py`: add a test for the new survivor, or list
it in `tools/mutants/known-aarch64.txt` with the reason it survives (an
equivalent change, a choice between equally correct paths, another
machine's code; `--write` rewrites the list, each new row's reason
`UNCLASSIFIED` until you write one).

CI (`.github/workflows/ci.yml`) runs the suites on Linux x86-64 and arm64
(without SME2, and without SHA-3 under QEMU), macOS, Windows with MSVC,
and wasm32, for every pull request from a fork, and by hand for a
candidate that changes code for those targets. `sh tools/check-builds.sh`
runs, in minutes, the builds the suites above leave out: without std, on
one CPU without SME2, warnings as errors, and compile checks for x86-64
and wasm32.

The supported targets are 64-bit Arm (Linux, macOS), x86-64 (Linux,
macOS, Windows with MSVC), and wasm32, with the latest stable Rust (and
any nightly feature the fork chooses to use). Official BLAKE3 serves the
rest.

The NEON hybrid assembly is generated and committed. Edit
`tools/gen_neon_hybrid.py`, then run
`python3 tools/gen_neon_hybrid.py > c/blake3_neon_hybrid_aarch64.S`;
a test fails when the two drift apart.

## Performance

Speed is the fork's purpose, so every change to `src/`, `c/`, `build.rs`,
`Cargo.toml`, or `Cargo.lock` passes a regression check first. The check
uses [bench-hashes](https://github.com/johnservil/bench-hashes), cloned
inside this checkout:

```sh
git clone https://github.com/johnservil/bench-hashes
pypy3 tools/perf_regress.py check       # the working tree against HEAD (python3 where PyPy is absent)
pypy3 tools/perf_regress.py compare OLD NEW
```

It builds the benchmark against both versions of the fork and runs them
alternately on the same machine, so it needs no stored numbers. Exit 0:
no cell slower; 1: a regression, its cells listed; 2: no verdict,
because other programs kept the machine busy during the check (run it
again on a quiet machine). `sh tools/install-git-hooks.sh` installs a pre-commit hook
that runs it for every commit that touches code. To run the full
benchmark against your working tree, see bench-hashes' `CONTRIBUTING.md`.

## Branches and changes

`servil` is the main line. Work happens on `candidate/<topic>`
branches; a candidate joins `servil` as a fast-forward once every check
above passes, mutation testing passes for a change to the Rust
(`tools/mutants/check.py`), the proofs pass for a change to an AArch64
kernel or the proof tools (QUALITY.md says how to run them), and the regression check finds no
slowdown on AArch64 Linux in a VM and natively on an Apple M4 Max. Pull requests are welcome
against `servil`; say in yours which machines you measured on.
