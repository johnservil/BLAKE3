# Notes for the sme2-bench maintainers

For whoever works on this branch next. `sme2-bench` is a fork of
BLAKE3 1.8.7 published as the crate `blake3-servil` (library `blake3_servil`) so it links beside
crates.io `blake3`. Its purpose is to be the fastest BLAKE3 on Apple
M4-class hardware, alone and beside other work. This file is what was
learned making it so; the commit messages on this branch carry the
numbers behind each change.

These notes concern this crate alone. The benchmark that scores it lives
in a separate repository with its own maintainers; treat it as a
customer that calls `blake3_servil::hash` and `blake3_servil::hash_multithreaded`,
prints `kernel_report()`, and reads the results. Do not tune to its harness; tune to the hardware.
Anything that helps only in a tight loop over one buffer will be found
out.

## Layout of the fork

| Piece | Where | Role |
|---|---|---|
| SME2 kernels | `c/blake3_sme2_aarch64.S`, `src/ffi_sme2.rs` | 16 chunks (or 16 parent blocks) per group on 512-bit streaming vectors; `DEGREE = 128` (8 groups per streaming-mode entry, amortising the ~0.5 µs mode switch) |
| Hybrid NEON kernels | `c/blake3_neon_hybrid_aarch64.S`, generated by `tools/gen_neon_hybrid.py`; `src/ffi_neon_hybrid.rs` | 1–15 chunks: scalar (k1), dup-layout `xar` pairs, classic quads, and integer+NEON hybrids running one or two scalar chunks *beside* NEON work |
| Scalar single-chunk path | `blake3_hybrid_c1` in the same `.S`; `hash_chunk`, `compress_in_place`, `compress_blocks` in `ffi_neon_hybrid.rs` | Every input ≤ 1 KiB in one kernel call; also the incremental `Hasher`'s single compressions |
| Multithreaded (`hash_multithreaded`, `hash_multithreaded_with_budget`) | `src/lanes.rs` (crate-internal) | Subtree split over execution lanes with fair-share admission; the public contract speaks of threads only |
| Kernel report (`kernel_report`, `kernel_report_multithreaded`) | `src/lib.rs` | Names the kernel by input length from the same run-time detection `hash` uses; the boundaries (1 KiB, 16 KiB, 128 KiB) live beside the kernels they describe, so a kernel change here means a report change here |
| Platform selection | `src/platform.rs` | `SME2` when detected with 512-bit SVL, else `NEON`; both route single compressions to the scalar kernel |

**The generated assembly is committed.** Edit `tools/gen_neon_hybrid.py`
and regenerate: `python3 tools/gen_neon_hybrid.py > c/blake3_neon_hybrid_aarch64.S`.
A test (`test_assembly_matches_generator`) fails if they drift.

## Where the time goes, by input size (Apple M4 Max, ns/B, single thread)

    ≤ 1 KiB   ~0.72–0.76   scalar c1, one call; bound by the G dependency chain
    2 KiB     ~0.50        k2 (one xar pair)
    3 KiB     ~0.36        k3: scalar beside a pair — the scalar chunk is free
    4–8 KiB   ~0.31–0.34   hybrids
    16–64 KiB ~0.21–0.23   SME2 groups begin; streaming-mode entry amortising
    ≥ 1 MiB   ~0.17–0.18   plateau

Upstream `blake3` on the same machine: 0.76 at 64 B, 0.42 at 4 KiB,
0.39 plateau. The fork leads at every size; the lead is 5–8% under
1 KiB and 2.2× at the plateau.

## Findings, roughly in the order they were made

### The single-chunk path (commit 220bed6)

The fork trailed upstream at 64–128 B by 4–5%. Four causes, all fixed:

1. `hash_all_at_once` inlined into `hash()` and dragged in
   `compress_subtree_to_parent_node`'s 6 KiB of CV arrays
   (`MAX_SIMD_DEGREE = 128`). Every call probed and zeroed that frame.
   `#[inline(never)]` on the subtree function fixed it; `hash()`'s frame
   is now 176 bytes. **Watch frame sizes whenever `MAX_SIMD_DEGREE`
   changes.**
2. k1 saved x19–x30 and d8–d15 though it uses neither d8–d15 nor
   x25–x30. Kernels now save only what they name (`callee_saved()` in
   the generator).
3. Per-block state (flags, counter, IV) reloaded from the frame at each
   block start. The lean k1 keeps them in registers and computes the
   next block's flags/length at the end of the previous block.
4. The final block and root compression went through the portable
   compressor with the CV crossing memory. `hash_chunk` does the whole
   chunk, root included, in one call. The packed-flags word gained a
   `last_len << 24` field so a kernel can record a short final block.

### Lanes (commits 9a97d45 → 79df26b)

**Model.** A lane is a set of CPUs sharing the resource the kernel
saturates. Apple: one SME unit per core cluster, so lanes = clusters
from `hw.perflevelN.physicalcpu / cpusperl2` (M4 Max: 2 P-clusters +
1 E-cluster = 3). Linux: measured once (two threads, 256 KiB each; ≥1.5×
slowdown ⇒ shared unit ⇒ lanes = sysfs clusters, else = CPUs). The
probe is noisy on a 2-vCPU VM; best-of-5 over ~2 ms timings settled it.
The module is private; the public API names no lanes. A caller caps
threads per call with `hash_multithreaded_with_budget(input, max_threads)`,
which bounds the lanes that call asks admission for. (An earlier
`BLAKE3_LANES` environment override is gone: the budget replaces it.)

**Admission** is the part that took the most iterations. What's there
now, and why:

- A single atomic word packs (lanes in use, active callers). Reading two
  separate counters let a caller see itself gone from one and present
  in the other.
- Fair share: `ceil(L / callers)`, never more than free. Without it, two
  threads hashing back-to-back each grabbed all lanes in the instant
  between the other's calls — turn and turn about, averaging to one
  lane each, *identical to single-threaded speed*. That was the
  M4 Max result that prompted the rework.
- A caller that finds its share held **waits** for it (≤ 20 ms,
  yielding). The holder returns within one input's time; the waiter
  then takes its half. Without the wait, the second arrival ran alone
  for a whole input.
- **There is no straggler/backoff rule.** There was one (stand down for
  16→4096 calls after workers ran late twice). It could not distinguish
  "another process has my CPU" from "an unrelated thread of my own
  process woke up", and in a benchmark it reached maximum backoff
  within seconds and ran everything serial. Cross-process fairness is
  the scheduler's job and it does it: two processes each hashing 2 MiB
  with lanes ran at 0.174/0.173 ns/B, the same as two serial processes.
  **Do not reintroduce a latency-based stand-down.**

**Splitting.** `split_subtrees` cuts the largest piece at its
left-subtree boundary until `count` pieces exist; every piece is a
valid subtree at its offset. For inputs where pieces stay ≥ 512 KiB,
cut `PIECES_PER_LANE = 4` per lane and deal largest-first to the lane
with least (`deal_to_lanes`). This fixed 3 MiB, which as 2 | 1 gave one
lane twice the work. Below 512 KiB one piece per lane: finer cuts of
1 MiB lost more to per-piece ramp-up than balance gained (0.108 vs
0.092 ns/B).

**Workers.** One resident thread per lane beyond the first. Poll the
queue for 200 µs *yielding between polls*, then sleep on a condvar.
The caller waits the same way. Two things learned the hard way:

- Waking a sleeping thread costs 30–300 µs on some systems (futex
  through a hypervisor). Hence the poll. `MIN_SPLIT_LEN = 128 KiB` is
  where a split pays for one hand-off.
- A thread that spins **without** yielding holds a scheduler quantum
  (~2 ms Linux). Two such threads on a 2-CPU box made a 29 µs split take
  2 ms because the worker couldn't get on. Every spin in this crate
  yields. Callers that spin-wait while we hash for them will see this
  too; it's documented in the module.

**The caller takes the largest share**, so on free lanes it's never
the one waiting.

### Things measured and rejected

- Rayon: 0.229 ns/B solo at 1 MiB on the 2-CPU VM, **0.456 beside a
  copy of itself** — slower than single-threaded upstream. Whole-machine
  work-stealing pools are what lanes exists to beat.
- 8 pieces for 1 MiB over 2 lanes: slower than 2 pieces (ramp-up).
- Straggler backoff: see above.
- `spin_loop` polls: see above.

## Results as of 79df26b (2-CPU Debian VM, ns/B, solo / beside a copy)

    1 MiB   serial 0.181 / 0.169    lanes 0.092 / 0.206
    8 MiB   serial 0.167 / 0.165    lanes 0.087 / 0.193

Lanes alone: 1.9× serial. Beside a copy: the pair share two lanes and
each runs near serial speed, which is the correct outcome on two CPUs.
On the M4 Max (3 lanes) two copies should get 2 + 1 lanes; run the
benchmark there to see it. The last M4 Max numbers on record predate
the admission fixes and are wrong (they showed lanes = serial).

## Next steps, in rough priority

1. **Verify on M4 Max.** Everything since 9a97d45 was validated on a
   2-CPU VM. The interesting cases (3 lanes, 2 callers; SME contention
   within a cluster; P vs E lanes) haven't been observed on real Apple
   hardware since the admission rework.
2. **E-cluster lane weight.** An E-core SME unit is slower than a P-core
   one, but `deal_to_lanes` gives every lane equal bytes. Measure the
   ratio once at startup (like the Linux probe) and weight the deal.
3. **Pieces below 512 KiB.** The ramp-up cost that made 8 pieces slower
   at 1 MiB is per-piece chunk-state startup plus one merge. If that
   drops, `MIN_BALANCED_PIECE_LEN` can drop and 3 MiB-shaped inputs at
   smaller sizes balance better.
4. **`MIN_SPLIT_LEN` on Apple.** 128 KiB was chosen on the VM where a
   wake costs ~30 µs. macOS wake latency is different; remeasure.
5. **Incremental `Hasher` over lanes.** Only the one-shot
   `hash_multithreaded` family is multithreaded. `Hasher::update` with a large slice could
   route through the same machinery.
6. **SME2 for 2–15 chunks?** Hybrids own that range now. Whether a
   partial-group SME2 kernel could beat k3–k10 at 3–15 chunks was never
   tried; streaming-mode entry (~0.5 µs) is the cost to beat.

## Testing

    cargo test --release --lib                      # 54 tests, ~0.3 s
    cargo test --release --features no_sme2 --lib   # NEON platform path
    cargo doc --no-deps                             # 7 warnings, all upstream's

The lanes tests check split shapes and subtree validity to 32 pieces,
merge for every piece count, results against `hash()` across the split
threshold and at 3 MiB, the admission arithmetic (`grant()` is pure),
and eight concurrent callers agreeing. Official test vectors, every
length 0..=4096 vs crates.io, and byte-at-a-time incremental were
checked externally at 220bed6 and 9a97d45; there's no in-tree harness
for that yet — worth adding.

On the Debian VM: `CC=clang-19 TMPDIR=/tmp` (system binutils predates
SME2). On macOS with Xcode ≥ 15, nothing special.
