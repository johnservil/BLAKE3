# Notes for the sme2-bench maintainers

For whoever works on this branch next. `sme2-bench` is a fork of
BLAKE3 1.8.7 published as the crate `blake3-servil` (library `blake3_servil`) so it links beside
crates.io `blake3`. Its purpose is to be the fastest BLAKE3 on Apple
M4-class hardware, alone and beside other work. This file is what was
learned making it so; the commit messages on this branch carry the
numbers behind each change.

These notes concern this crate alone. The benchmark that scores it lives
in a separate repository with its own maintainers; treat it as a
customer that calls `blake3_servil::hash` and `blake3_servil::hash_multithreaded`,
prints `kernel_report()`, and reads the results. Do not tune to its harness; tune to the hardware.
Anything that helps only in a tight loop over one buffer will be found
out.

## Layout of the fork

| Piece | Where | Role |
|---|---|---|
| SME2 kernels | `c/blake3_sme2_aarch64.S`, `src/ffi_sme2.rs` | 16 chunks (or 16 parent blocks) per group on 512-bit streaming vectors; `DEGREE = 128` (8 groups per streaming-mode entry, amortising the ~0.5 µs mode switch) |
| Hybrid NEON kernels | `c/blake3_neon_hybrid_aarch64.S`, generated by `tools/gen_neon_hybrid.py`; `src/ffi_neon_hybrid.rs` | 1–16 chunks: scalar (k1), dup-layout `xar` pairs, classic quads, and integer+NEON hybrids running one or two scalar chunks *beside* NEON work; `Platform::NEON` has degree 16 and leads with k10 (VM: k4 0.289 ns/B, k10 0.212) |
| Scalar single-chunk path | `blake3_hybrid_c1` in the same `.S`; `hash_chunk`, `compress_in_place`, `compress_blocks` in `ffi_neon_hybrid.rs` | Every input ≤ 1 KiB in one kernel call; also the incremental `Hasher`'s single compressions |
| Multithreaded (`hash_multithreaded`, `hash_multithreaded_with_budget`) | `src/lanes.rs` (crate-internal) | One pool over every CPU: jobs in a lock-free slot table, pieces pulled through a cursor, SME2 permits per SME unit, NEON hybrids on the other cores; the public contract speaks of threads only |
| Kernel report (`kernel_report`, `kernel_report_multithreaded`) | `src/lib.rs` | Names the kernel by input length from the same run-time detection `hash` uses; the boundaries (1 KiB, 16 KiB, 64 KiB) live beside the kernels they describe, so a kernel change here means a report change here |
| Platform selection | `src/platform.rs` | `SME2` when detected with 512-bit SVL, else `NEON`; both route single compressions to the scalar kernel. `Hasher::set_platform` (crate-internal) lets a pool piece name its kernels |

**The generated assembly is committed.** Edit `tools/gen_neon_hybrid.py`
and regenerate: `python3 tools/gen_neon_hybrid.py > c/blake3_neon_hybrid_aarch64.S`.
A test (`test_assembly_matches_generator`) fails if they drift.

## Where the time goes, by input size (Apple M4 Max, ns/B, single thread)

    ≤ 1 KiB   ~0.72–0.76   scalar c1, one call; bound by the G dependency chain
    2 KiB     ~0.50        k2 (one xar pair)
    3 KiB     ~0.36        k3: scalar beside a pair — the scalar chunk is free
    4–8 KiB   ~0.31–0.34   hybrids
    16–64 KiB ~0.21–0.23   SME2 groups begin; streaming-mode entry amortising

Upstream `blake3` on the same machine: 0.76 at 64 B, 0.42 at 4 KiB,
0.39 plateau. The fork leads at every size; the lead is 5–8% under
1 KiB and 2.2× at the plateau.

## Findings, roughly in the order they were made

### The single-chunk path (commit 220bed6)

The fork trailed upstream at 64–128 B by 4–5%. Four causes, all fixed:

1. `hash_all_at_once` inlined into `hash()` and dragged in
   `compress_subtree_to_parent_node`'s 6 KiB of CV arrays
   (`MAX_SIMD_DEGREE = 128`). Every call probed and zeroed that frame.
   `#[inline(never)]` on the subtree function fixed it; `hash()`'s frame
   is now 176 bytes. **Watch frame sizes whenever `MAX_SIMD_DEGREE`
   changes.**
2. k1 saved x19–x30 and d8–d15 though it uses neither d8–d15 nor
   x25–x30. Kernels now save only what they name (`callee_saved()` in
   the generator).
3. Per-block state (flags, counter, IV) reloaded from the frame at each
   block start. The lean k1 keeps them in registers and computes the
   next block's flags/length at the end of the previous block.
4. The final block and root compression went through the portable
   compressor with the CV crossing memory. `hash_chunk` does the whole
   chunk, root included, in one call. The packed-flags word gained a
   `last_len << 24` field so a kernel can record a short final block.

### Lanes, first design (commits 9a97d45 → 79df26b; replaced)

One worker per *lane* (a set of CPUs sharing an SME unit), fair-share
admission of lanes between concurrent callers with a 20 ms wait, pieces
dealt to lanes up front. It used three threads on an M4 Max and lost to
the single-threaded call at every size from 128 KiB under duo. What
survives from it: the subtree cut and merge, the yielding polls, and the
warning against a latency-based stand-down (below).

### The pool (commit b3b4bc8)

**Model.** Every CPU hashes; the SME units are the scarce resource. A
piece runs on the SME2 kernels while a *permit* (one per SME unit) is
free, else on the NEON hybrids, which every core runs at full speed
(VM: SME2 6.6 GB/s per unit, ~3 units; NEON 3.6–4.5 GB/s per core, 16
cores, 57 GB/s in all). Unit count: clusters from sysctl on Apple;
on Linux measured once, in the background, as the thread count at which
the aggregate SME2 rate stops growing (`measure_sme_units`; sysfs
cluster topology is the hypervisor's invention on a VM).

**Jobs (current).** A call registers its pieces, cursor, active-thread
count, and thread cap in the slot table. Workers serve calls round-robin.
The caller exhausts its cursor, clears its slot, drains readers still
reserving work, then waits for the active count to reach zero. That one
count both limits accepted reservations and publishes completed outputs.
The separate completion count and pool-wide busy-worker count are gone.

A call arriving when concurrent callers already fill the CPUs hashes its
input whole, using the same SME-permit policy as workers. This replaces
per-piece global admission with one decision per call. The fixed pool
has `cpus - 1` workers; calling threads and existing workers can overlap.
The public thread budget remains exact for each call. A one-CPU machine
uses the whole-input path (the previous cut could produce a single piece
and panic while merging it).

**Pieces** shrink toward the end (`next_piece_len`: about remaining /
threads, a power of two chunks, 8–128 KiB), so the slowest thread's last
piece is small. Before this, one slow vCPU holding a 128 KiB piece set
the finish of a 2 MiB solo call at 105 µs; after, 65 µs. Pieces are in
offset order; the merge (`subtree_cv`) walks the tree by
`partition_point`.

**Memory traffic.** Fifteen pollers doing `fetch_add`/`fetch_sub` on a
slot's line every poll stalled a caller's `register` (one CAS) by
10–150 µs. Polls are loads only; RMWs happen once a job is visible. The
job's `cursor` and `active` each sit on their own cache line
(`Line`, 128-byte aligned).

**Sleep and wake.** A wake costs the waker 12–20 µs on the VM and the
sleeper arrives 40–60 µs later (`examples/wake.rs`). Rules that came out
of that: workers sleep only when no job has been *registered* for
`SPIN_BEFORE_SLEEP` (200 µs), so a worker that lost the race for a
piece stays up while calls keep coming; a call whose pieces outnumber
the awake workers wakes every sleeper in one `notify_all`; a woken
worker returns to polling rather than re-waiting; nobody wakes anyone on
a hashing thread's critical path.

**Start-up is part of the contract.** `initialize()` creates the pool:
it measures the SME unit count where the platform reports no topology
(Linux; about 40 ms on the 16-vCPU VM, every CPU busy) and spawns the
workers, then returns. The first multithreaded call that leaves its
thread does the same when the program has yet to call it, and the public
docs say so: up to tens of milliseconds, once. An earlier design hid the
start behind a starter thread so the first call cost a call; it was there
because a synchronous start once landed inside bench-hashes' calibration
probe and pinned the 64 KiB cell at one cold call per sample. The
benchmark now calls every contender at every size in its correctness
checks before calibrating, so the start lands there, and the documented
contract replaces the hidden mechanism.

**The SME2 ↔ NEON transition** (`examples/transition.rs`). On the VM the
first NEON load/store after the SME2 kernel costs ~4 µs; SME2 kernel
calls back to back cost nothing extra; scalar and FP code between them
is free. Every piece on an SME2 thread pays one round trip (the parent
levels below sixteen and the chaining-value copy use NEON). The notes'
degree measurements on an M4 imply ~1 µs there. Consequence: long pieces
for SME2 threads; and on the VM three permits tie with none, because
4 µs on a 26 µs piece is what SME2 gains over NEON. Permits stay for the
M4, where SME2 is 1.5–2× NEON per thread and the round trip a quarter.

### Things measured and rejected

- **Wake cascades.** A woken worker waking the next before its piece:
  the wake sat on the hashing path (64 KiB duo 1.15 ns/B in the
  interleaved pattern). After its piece: 0.44. One `notify_all` from
  the caller, with workers staying awake while jobs keep coming: 0.20.
  Delegating that `notify_all` to the first woken worker: 0.22–0.36
  (the rest arrive a wake later; the callers work alone meanwhile).
- **Longer spins.** `SPIN_BEFORE_SLEEP` of 10 ms on the VM: fifteen
  yield-spinning vCPUs starve the two callers of host time (64 KiB
  interleaved duo 1.3 ns/B). A native machine would not show this;
  200 µs stays.
- **Splitting from 32 KiB.** 32 KiB duo 0.345 vs 0.225 serial, 48 KiB
  0.251 vs 0.220; 64 KiB stays the threshold.
- **Smaller minimum pieces at 256 KiB.** 8 KiB pieces where 16 KiB fit
  lost 20% there; the shrinking schedule makes both moot.
### Rejected earlier (still true)

- Rayon-style whole-machine work-stealing pools, one per caller: two of
  them halve each other. One pool shared by every caller is the answer.
- Straggler backoff / latency-based stand-down: cannot tell another
  process from an unrelated thread of its own; stood down for good.
  **Do not reintroduce.**
- `spin_loop` polls without yielding: hold a scheduler quantum.

   the simplifications below have VM measurements and await native tests.
2. **Bulk latency.** SIMD merging is implemented. At 3–8 MiB, VM timings

   the smallest pieces itself, or the cut could end finer still.

## Session: simpler pool, correctness checks, September 2026

The shared principles now live in both AGENTS.md files: conceptual ease,
less code and state, fewer runtime regimes, and fixed known-output tests.
Favor changes that improve simplicity and efficiency together.

Kept changes:

- Pieces use the existing one-shot subtree code. Its counter and platform
  are explicit; the duplicate OwnedMode and per-piece incremental Hasher
  setup are gone. Jobs own key words and flags directly.
- The caller merges CVs by SIMD levels, in place. The previous recursive
  merger remains only as a structural test oracle.
- One active counter handles per-call budgets and completion. A reservation
  atomically increments before testing the cap and undoes a failed attempt.
  This fixes the old load-then-increment race. Unregister drains slot readers
  before a caller waits for zero, so no later reservation can reach its job.
- Global admission is once per call, rather than once per worker piece.
  Whole-input calls share the same SME permits as workers, including at
  high caller counts. Redundant unsafe Send/Sync implementations and the
  unused total-permit cache were removed.

Discarded experiments: equal-size pieces (bulk regressions), occupied-slot
bitmap and extra cache-line padding (extra state or scan traffic), retaining
CPU reservations across pieces, broader fixed-width recursion, and changing
small parent reductions' platform. The measurements did not justify them.
No tuning environment variables or benchmark-specific input/caller checks
remain. Scratch experiments and raw logs are in `/workspace/tmp/mt-session/`.

### Validation and the benchmark

Default tests: 56 library + 15 doc; no_sme2: 55 + 15; pure: 46 + 15;
Rayon library: 57; debug library: 56; no-default-features check passes.
ARM-specific diagnostic examples now compile to a clear availability
message on builds without NEON, including pure builds.
New tests compare SIMD and recursive merges on arbitrary CVs through
64 MiB cuts, enforce caps under simultaneous reservations, and run 32
concurrent callers with mixed budgets. One- and two-CPU affinity checks pass.

The benchmark now checks every timed input and boundary vectors before
calibration, with serial and simultaneous calls through the same dispatch
as timing. Its 64 checked-in golden vectors come from independent BLAKE3
reference code and Python hashlib; runtime checks never regenerate expected
answers. Three benchmark tests cover all available implementations, published
empty-input hashes, and fail-stop mismatch diagnostics. The fork retains its
existing published-vector/reference tests; further golden-vector expansion
there is follow-up work, not a prerequisite for using fixed vectors under
concurrent schedules.
