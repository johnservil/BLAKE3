# Quality assurance: what we check, and how you can check it

This page lists every step we have taken to make the servil fork of
BLAKE3 compute correct digests and stay memory-safe. For each step it
gives the command that reproduces it on your own machine. It also lists
the bugs those steps found and what formal verification we have tried.

Short version: every kernel and entry point is tested against the
BLAKE3 reference implementation and fixed published digests, and every
process re-checks each assembly kernel against fixed answers before it
first hashes. The code
has run under AddressSanitizer, ThreadSanitizer, and Miri, and against
inaccessible guard pages, and a few of its index calculations are proved
with the Kani model checker. No human has yet reviewed it line by line,
and nobody has audited it. The [README's warning](README.md) stands.

## What is new, and so where the risk is

The fork keeps upstream BLAKE3 1.8.7's algorithm code, its portable
Rust, and its x86 kernels, and adds code of its own:

- AArch64 kernels: SME2 assembly for Apple M4 and later
  (`c/blake3_sme2_aarch64.S`), and integer + NEON kernels generated by
  `tools/gen_neon_hybrid.py` and `tools/gen_sme2_hybrid.py`;
- a pool of worker threads for multithreaded hashing (`src/lanes.rs`);
- batches of many messages in one call (`hash_many`, `src/many.rs`);
- `Stream`, which hashes behind the caller (`src/stream.rs`).

Everything below aims at this new code. Much of it is `unsafe`: assembly,
pointer tables, uninitialised scratch buffers, and threads that share
the caller's buffers.

## Correctness: every answer checked against an independent one

**Fixed answers.** The tests compare digests with answers that come
from outside the fork's optimized code: upstream's published test
vectors (`test_vectors/`) and the reference implementation
(`reference_impl/`, a separate, simple Rust implementation), and tests
never regenerate their own expected answers. (The benchmark checks no
digests; correctness is these tests' business.)

**The test suites** (the fork's `src/test.rs` and each module's tests),
among them:

- every chunk count and every partial length of every NEON kernel,
  against the portable compressor;
- every input length from one chunk and a byte to seventeen chunks,
  against the reference implementation;
- every platform's batch kernel at every input shape (1 to 16 blocks,
  keyed flags, a counter whose low word overflows mid-batch, pointer
  tables forward, reversed, and strided), against the portable one;
- `hash_many` at every message length from 0 to 3000 bytes on every
  platform the CPU has, against the reference implementation, and at
  counts that fill and leave remainders in every group size, single- and
  multithreaded, against one `hash` call per message;
- the pool's cuts and merges, its thread caps, and 32 callers at once;
- the same suites in the builds without SME2 (`no_sme2`) and without any
  SIMD (`pure`).

**The benchmark checks too.** bench-hashes checks every digest it times,
outside the timed intervals, against its frozen answers.

**Every process checks itself before its first hash.** The tests prove
the code on our machines; a user's machine may have a compiler that
miscompiles, a linker that mislinks, or a CPU with a faulty vector or
matrix unit. So the first call in a process (or `initialize()`) hashes 39
fixed inputs and compares each result with the reference implementation's
answer, checked into the source (`src/self_test.rs`) and verified there
by a unit test. The inputs are chosen so that together they run every one
of the AArch64 assembly kernels, all 31 entry points, counted with gdb
breakpoints (`tools/self_test_coverage.py`), along with the batch,
keyed, key-derivation, incremental, and extended-output paths. As Niels
Ferguson suggested, each case's output feeds the next case's input, so
a fault anywhere changes every result after it, and the inputs use
unusual alignments, lengths, and padding, where platform, compiler, and
hardware faults hide from ordinary tests. A wrong result stops the
program with a panic naming the failing path. The check costs 0.1 to
0.2 ms once per process; most of it is the first fetch of 390 KB of
unrolled kernel code.

## Memory safety

- **Guard pages** (`test::guard_pages`). The sanitizers cannot see
  inside assembly, so these tests put each kernel's input, then its
  output, flush against an inaccessible page (after the buffer, then
  before it). A kernel that reads or writes a single byte outside its
  buffers crashes the test. They cover `hash` at every length to
  2 KiB + 70 and around chunk counts up to 1025, and `hash_many` at 15
  message lengths and 20 counts.
- **AddressSanitizer** over the library tests: clean. As a control, a
  deliberate heap overflow in a small program was caught.
- **ThreadSanitizer** over the pool, stream, and batch tests, 30 runs:
  clean. A deliberate data race in a control program was caught.
- **Miri**, which interprets Rust and stops at undefined behaviour, over
  small versions of the unsafe paths (`test::unsafe_paths`: batches, the
  pool with two callers, a stream past one buffer) in the `pure` build
  (Miri cannot run assembly or SIMD intrinsics): all four tests pass, in
  41 minutes. Miri then reports that the pool's worker threads were still
  running when the program ended; they live for the whole process by
  design, and `-Zmiri-ignore-leaks` accepts that.
- **Coverage.** LLVM's source coverage over the library tests reaches
  93% of lines. The unexercised paths it showed became new tests (the
  guard-page tests among them). The rest is code for platforms the test
  machine lacks (x86, AArch64 without the SHA-3 extension) and
  fail-stop branches.

## Proofs

We use [Kani](https://github.com/model-checking/kani), a bounded model
checker for Rust. For every input, not just sampled ones, it proves:

- the pool's piece length is a power of two within its bounds and near a
  thread's share of what remains, for every remaining length and 1 to
  256 threads;
- each step of the pool's cutting loop keeps its invariant, so by
  induction every piece is a whole BLAKE3 subtree at its offset, for
  every input length (the hash would be wrong otherwise);
- a batch message's slot is whole 64-byte blocks and holds the message;
- the pointer table built for a batch, which an `unsafe` block reads,
  holds only slots it wrote, each pointing at the right message (up to 20
  lanes; the kernels take up to 144).

A positive control: with a deliberate off-by-one in the piece length,
Kani reports the broken bound and a counterexample.

## Check it yourself

On an Apple Silicon Mac, or on Linux with a C compiler that assembles
SME2 (clang 17 or later; set `CC=clang-19` or similar):

```sh
git clone -b servil https://github.com/johnservil/BLAKE3 && cd BLAKE3
cargo test --release --lib                        # 89 tests
cargo test --release --lib --features no_sme2     # 85
cargo test --release --lib --features pure        # 74
cargo test --release --doc                        # 21
cargo test --release --manifest-path test_vectors/Cargo.toml
```

The sanitizers and Miri need nightly Rust
(`rustup toolchain install nightly --component miri,rust-src,llvm-tools`):

```sh
RUSTFLAGS="-Zsanitizer=address" cargo +nightly test -Zbuild-std --target aarch64-unknown-linux-gnu --release --lib
RUSTFLAGS="-Zsanitizer=thread" cargo +nightly test -Zbuild-std --target aarch64-unknown-linux-gnu --release --lib
MIRIFLAGS="-Zmiri-num-cpus=4 -Zmiri-ignore-leaks" cargo +nightly miri test --features pure --lib -- unsafe_paths test_miri_smoketest
```

(On macOS, use the target `aarch64-apple-darwin`.) The proofs need Kani
(`cargo install --locked kani-verifier && cargo kani setup`; on Debian 12,
whose glibc is older than recent Kani bundles need, `--version 0.64.0`):

```sh
cargo kani
```

Timing claims are checked the same way: [bench-hashes](https://github.com/johnservil/bench-hashes)
measures the fork against the official crate and others on your machine.

## The bugs these steps found

Four, all fixed; none reached the results of a documented function. Each entry
names the commit that introduced the code and the one that fixed it, in
[github.com/johnservil/BLAKE3](https://github.com/johnservil/BLAKE3).

1. **The SME2 message kernel mishandled one-block messages**
   (`c/blake3_sme2_aarch64.S`, `blake3_sme2_hash16_messages_512`). Given
   messages of a single block, it compressed a first block, then ran the
   same block again as the last one, and left out the chunk-start flag
   on it. The digests would have been wrong. It came with the kernel
   (220de01), whose callers then passed only messages of two or more
   blocks. The tests of the first caller with one-block messages (the
   side-by-side chunk path) caught it before that path landed. Fixed in
   03ffc95: a one-block message now starts and ends on its last block.
2. **`Platform::hash_many` dropped the tail of an input that was not
   whole blocks** (`src/platform.rs`). This hidden, unstable function
   takes a message length as a type parameter. A length that was not a
   multiple of 64 bytes lost its last partial block with no error, so two
   messages that differed only in those bytes got the same digest. The
   fork inherited this from the official crate, where it persists in
   release builds; the fork's own callers always pass whole blocks.
   Coverage-driven tests found it; fixed in d395f9e: such a length is now
   a compile-time error. We reported it upstream
   ([BLAKE3-team/BLAKE3#590](https://github.com/BLAKE3-team/BLAKE3/issues/590),
   with a fix in [#591](https://github.com/BLAKE3-team/BLAKE3/pull/591)),
   together with a catalog of the public projects that call the function:
   each of them passes whole blocks.
3. **A batch path asserted on a CPU combination that does not exist**
   (`src/many.rs`, `hash_blocks`). It decided whether to use the padded
   SME2 group from the length of its pointer table. On SME2 without the
   SHA-3 extension, the fallback's spare lane made that length look like
   a padded group, and an assertion stopped the program. Every real CPU
   with SME2 also has SHA-3, so the case could not arise. Introduced in
   1ca0b1d, found by a new test of the fallback arrangement on SME2, and
   fixed in d395f9e: the function now records its own choice.
4. **A `Stream` branch would have hashed only the last buffer**
   (`src/stream.rs`, `finalize_handed_over`). After the stream had
   handed buffers to its hashing thread, `finalize` had a branch for "no
   hashing thread", which would have hashed the final buffer alone. That
   state cannot occur once a buffer has been handed over. Introduced in
   59ad5c1, found by coverage; fixed in d395f9e: the branch is now a
   fail-stop `expect`.

## Formal verification: what we tried and considered

- **Kani** (bounded model checking): tried, with the results above. The
  first attempt, a single proof of the whole cutting loop over inputs up
  to 2 MiB, ran out of memory even at 96 KiB and with every solver we
  tried. Proving one loop step and arguing by induction proved more, in
  under two seconds. One proof with an unbounded symbolic thread count
  ran for hours without an answer, and bounding the count settled it. A
  proof over all 144 lanes of the batch pointer table did not finish
  within 7 minutes, when we stopped it; 20 lanes take 45 seconds. Kani cannot look inside
  the assembly kernels or C code.
- **Miri**: used (above). It checks the executions it runs, which falls
  short of a proof, and it cannot run assembly or intrinsics.
- **Deductive verifiers for Rust (Verus, Prusti, Creusot, Aeneas)**:
  considered, not tried yet. They could prove the pool and the batch
  paths correct for every input and every thread interleaving. The cost
  is annotating or restructuring the code (atomics, raw pointers,
  uninitialised memory), and the kernels would still sit outside the
  proof.
- **hax to F\* or Rocq** (as used for libcrux): considered, not tried
  yet. It suits proving the portable Rust equal to BLAKE3's
  specification. That code is upstream's and the least changed.
- **SAW with a Cryptol specification**: considered, not tried yet. It
  proves C or LLVM code equal to a specification, and could cover the C
  NEON kernel. It does not model SME2.
- **The SME2 assembly**: we know of no production verification tool that
  models SME2. Arm's machine-readable architecture specification
  includes SME, and research tools built on it (Sail, Isla) could in
  principle check the kernel symbolically. That would be a research
  project. Until then the kernel rests on the tests: the reference
  answers, every shape and count, and the guard pages.
- **Constant-time behaviour**: not checked. By design the kernels branch
  only on lengths and counts, never on the data. That matters to users
  of the keyed mode, and a tool such as dudect or ctgrind would test it.
- **Fuzzing (cargo-fuzz)**: not used. The tests enumerate every kernel
  at every input shape, count, and boundary against fixed answers, the
  paths a fuzzer would search for.

## Not yet done

No person has reviewed the code line by line, and nobody has audited it.
The test suites have run on an Apple M4 Max, under macOS and in a
Debian 12 AArch64 VM on it (whose SME2 unit the VM exposes); the
sanitizers, Miri, and Kani in the VM. The fork compiles for x86-64 but
has not been tested on x86-64 hardware yet.
