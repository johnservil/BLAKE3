# Quality assurance: what we check, and how you can check it

This page lists every step we have taken to make the servil fork of
BLAKE3 compute correct digests and stay memory-safe. For each step it
gives the command that reproduces it on your own machine. It also lists
the bugs those steps found and what formal verification we have tried.

**In brief.** On Apple Silicon and other 64-bit Arm CPUs:

- **The assembly kernels are proved right.** Every assembly kernel but
  one (NEON, integer, and SME2) is proved to compute the BLAKE3
  standard's compression function for every input, key, counter, and
  flags value, as the CPU runs it; each reads and writes only its own
  buffers and takes a path that depends only on lengths. The one, the
  SME2 kernel that adds an integer lane (`c/blake3_sme2_hybrid_aarch64.S`),
  runs inside SME2 hashes of 256 KiB and more, and is tested.
- **The Rust code around the kernels is tested**, and the tests are
  checked themselves (below); proofs are kept for the assembly, which
  testing reaches least.
- **Every answer is also tested** against upstream's published vectors
  and an independent reference implementation, and each process checks
  its kernels against fixed answers before its first hash.
- **The tests are checked themselves**: mutation testing plants likely
  bugs throughout the library's Rust, one at a time, and each that every
  test survives is listed with its reason.
- **Memory safety is tested** under AddressSanitizer, ThreadSanitizer,
  Miri, and guard pages around every kernel's buffers.

On x86-64 the fork's own code is tested, its kernels among them (Devon
Jonte's passes of whole chunks and a partial one, in Rust intrinsics, beside
upstream's assembly), and the proofs cover AArch64. The code awaits a line-by-line human
review and an audit; the [README's warning](README.md) stands. "Proofs" states
each claim precisely, with what it rests on; "What each check would
catch" says which kinds of bug each step finds.

## What is new, and so where the risk is

The fork keeps upstream BLAKE3 1.8.7's algorithm code, its portable
Rust, and its x86-64 kernels, and adds code of its own:

- AArch64 kernels: SME2 assembly for Apple M4 and later
  (`c/blake3_sme2_aarch64.S`), and integer + NEON kernels generated by
  `tools/gen_neon_hybrid.py` and `tools/gen_sme2_hybrid.py`;
- x86-64 kernels in Rust intrinsics that hash whole chunks and a partial
  one in one pass, four lanes on SSE4.1 and eight on AVX2
  (`src/rust_sse41.rs`, `src/rust_avx2.rs`), with batches across
  messages and a two-input path (`src/many.rs`, `src/pair.rs`);
- a pool of worker threads for multithreaded hashing (`src/lanes.rs`);
- batches of many messages in one call (`hash_many`, `src/many.rs`),
  collections of messages and many hashers at once (`hash_each_with`,
  `Hasher::update_each`, `src/each.rs`);
- the stream, which hashes the program's messages behind it, each digest
  into the place the program names (`stream`, `src/stream.rs`). (The
  queue it replaced, `src/queue.rs`, retired on October 16, 2026; the
  records below that name it describe its time.)
- outboards and their verification (`outboard_with`, `Verifier`,
  `src/outboard.rs`);
- the startup self-test (`src/self_test.rs`);
- the C API (`capi/b3.h` over the crate, `capi/src/lib.rs`), tested
  through every call against the official test vectors, and from a C
  program compiled as C11 with every warning an error (`capi/tests/`).

Everything below aims at this new code. Much of it is `unsafe`: assembly,
pointer tables, uninitialised scratch buffers, and threads that share
the caller's buffers.

## Correctness: every answer checked against an independent one

**Fixed answers.** The tests compare digests with answers that come
from outside the fork's optimized code: upstream's published test
vectors (`test_vectors/`) and the reference implementation
(`reference_impl/`, a separate, simple Rust implementation), and tests
never regenerate their own expected answers. (The benchmark checks no
digests; correctness is these tests' business.)

**How a test chooses its inputs.** Each test checks the cases its code
can tell apart, and only those: every branch, and every arithmetic case
that changes what the code does (a boundary such as a block's last byte,
a count either side of a threshold, a remainder of each size). The cases
come from reading the code, and each test computes its list from the
code's own constants (`BLOCK_LEN`, `CHUNK_LEN`, a kernel group's size,
the dispatch's thresholds), so a list moves with the code it covers; a
change to the code's cases changes its tests in the same commit.
Inputs within one case run the same code on different data, so they add
time and no evidence: no test enumerates every length or draws random
inputs. (Every input of the assembly kernels is covered by proof, not by
tests; the tests check the calls into them, and every other platform.)

**How the choice is checked**, mechanically:

- *Branch coverage* (`cargo llvm-cov --branch`, LLVM's per-branch
  counts): a test that replaces another reaches every branch side the old
  one reached. Replacing the exhaustive and random tests (October 2026)
  kept or raised each one's coverage, at a fraction of the inputs:
  `hash_many` from every length to 3000 bytes to each length case, one
  to seventeen chunks from 16,384 lengths to 513, the `Hasher`'s random
  updates by three updates at each staging boundary (202 to 216 branch
  sides), the extended output's random reads by each read case (200 to
  207).
- *Mutation testing* (`cargo mutants`): it plants the likely future bug
  (`<` for `<=`, a constant or an operand off by one, a condition
  inverted) one at a time and requires a test to fail. A mutant every test
  survives is one of three things: a missing case (the test gains it), a
  change between equally correct paths (a speed threshold, listed as
  such), or code that does nothing (removed).

**What mutation testing finds**, over the whole library on the VM
(October 17): of 2614 mutants, 1772 fail a test or hang, and 169 do not
compile. Each of the other 673 is listed with its reason in
`tools/mutants/known-aarch64.txt`: code for another machine (x86, a CPU
without SME2 or the SHA-3 extension, one CPU), a choice between equally
correct paths (what to prefetch, a speed threshold, how work is cut
among threads), or an equivalent change (`|` made `^` on flag bits that
never overlap). Two groups stay open: the thread pool's scheduling under
interleavings that the tests leave to chance (Loom would force them),
and the queue and the pool's job scheduler, which the stream replaces.
Earlier runs found missing cases (in `Hash`, the `Hasher`,
`OutputReader`, `update_each`, the self-test) and dead code, each fixed.
By function, of the library's 398 functions with mutants, 253 have every
mutant caught, 109 every survivor explained, and 36 an open survivor (in
the two groups above); the assembly kernels are the proofs'.
`tools/mutants/check.py` reruns every mutant, reruns alone any whose
outcome differs from the list (so a test that fails by chance, under
load, decides nothing), and fails on a survivor not listed, a listed one
now caught, or a listed one without a reason; it runs before each
promotion that changes the library's Rust (44 minutes on the VM).

**What the suites cover now**, on the VM: 88% of the library's branch
sides (906 of 1026), over the default, one-CPU, and no-std runs. Most of
the rest are the branches of other machines (the std build on a CPU
without the SHA-3 extension or without SME2, which CI's AArch64 job now
runs), the pool's and the queue's scheduling races, and fail-stop arms.
The aim is
every branch side of the code users run, each one reached by a test or
named as unreachable in the code, and every mutant either caught or
explained; a branch that is not worth a test is a sign the branch is not
worth keeping.

**The suites** (the fork's `src/test.rs` and each module's tests), among
them: every case of `hash_many` on every platform the CPU has, and of the
one-shot hash from one to seventeen chunks, against the reference
implementation; every platform's batch kernel at every input shape (1 to
16 blocks, keyed flags, a counter whose low word overflows mid-batch,
pointer tables forward, reversed, and strided), against the portable one;
the pool's cuts and merges, its thread caps, and 32 callers at once; and
the same suites in the builds without SME2 (`no_sme2`) and without any
SIMD (`pure`).

**Every process checks itself before its first hash.** The tests prove
the code on our machines; a user's machine may have a compiler that
miscompiles, a linker that mislinks, or a CPU with a faulty vector or
matrix unit. So the first call in a process (or `initialize()`) hashes 42
fixed inputs and compares each result with the reference implementation's
answer, checked into the source (`src/self_test.rs`) and verified there
by a unit test. The inputs are chosen so that together they run every one
of the AArch64 assembly kernels, every entry point, which a unit test
checks on every run (`test_self_test_runs_every_kernel`, from the code's
own kernel tables), along with the batch,
keyed, key-derivation, incremental, and extended-output paths. As Niels
Ferguson suggested, each case's output feeds the next case's input, so
a fault anywhere changes every result after it, and the inputs use
unusual alignments, lengths, and padding, where platform, compiler, and
hardware faults hide from ordinary tests. A wrong result stops the
program with a panic naming the failing path. The check costs 0.1 to
0.2 ms once per process; most of it is the first fetch of 390 KB of
unrolled kernel code.

## Memory safety

- **Guard pages** (`test::guard_pages`). The sanitizers cannot see
  inside assembly, so these tests put each kernel's input, then its
  output, flush against an inaccessible page (after the buffer, then
  before it). A kernel that reads or writes a single byte outside its
  buffers crashes the test. They cover `hash` at every length to
  2 KiB + 70 and around chunk counts up to 1025, `hash_many` at 15
  message lengths and 20 counts, and extended output at 10 lengths from
  three positions.
- **AddressSanitizer** over the library tests: clean. As a control, a
  deliberate heap overflow in a small program was caught.
- **ThreadSanitizer** over the pool, stream, and batch tests, 30 runs:
  clean. A deliberate data race in a control program was caught.
- **Natively on the M4 Max** (October 2, 2026; probe/mac-debug-tests,
  jobs 996-998, and again on servil 1d2b652 and ff8f203, jobs 1031 and
  1083): every suite in debug builds (overflow checks and debug
  assertions over the SME2 paths), AddressSanitizer over the library
  tests, the planned API's tests, and the queue's allocation test, and
  ThreadSanitizer over the pool, unsafe-path, and batch tests and the
  planned API's (the queue among them; std itself uninstrumented): all
  clean.
- **CI on other targets** (GitHub Actions): the suites on Linux x86-64
  and arm64 (without SME2, and without SHA-3 under QEMU), macOS, Windows
  with MSVC, and wasm32 (wasmtime).
- **Miri**, which interprets Rust and stops at undefined behaviour, over
  small versions of the unsafe paths in the `pure` build (Miri cannot run
  assembly or SIMD intrinsics): `test::unsafe_paths` (batches, the pool
  with two callers; 13 minutes in the VM) and, since October 2,
  `queue::test::test_miri_queue_round_trips` (every shape of queue, its
  short messages gathered and its long ones as the pool's tasks; 5
  minutes), which CI's Miri step runs: all pass, on six scheduling seeds
  for the queue. It found bug 7 below. The pool's and the queue's
  threads live for the whole process by design, and `-Zmiri-ignore-leaks`
  accepts that.
- **Coverage.** LLVM's source coverage over the library tests reaches
  93% of lines. The unexercised paths it showed became new tests (the
  guard-page tests among them). The rest is code for platforms the test
  machine lacks (x86, AArch64 without the SHA-3 extension) and
  fail-stop branches.

## Proofs

### What is proved

On AArch64 (Apple Silicon, and other 64-bit Arm CPUs), every assembly
kernel but the SME2 hybrid kernel (the NEON and integer kernels in
`c/blake3_neon_hybrid_aarch64.S`, the SME2 kernels in
`c/blake3_sme2_aarch64.S`) is proved to compute what
[C2SP's BLAKE3 standard](https://c2sp.org/BLAKE3) specifies, for every
input, key, counter, and flags value: each output word equals the
standard's. The SME2 kernels are proved at the 512-bit vector length of
Apple's M4, and the chunk, parent, message, and extended-output kernels
at every group count, by induction over their group loops. Each kernel
also reads and writes only its own buffers, keeps the calling
convention, and takes a path that depends only on lengths.

The Rust code (the dispatch, the tree walk, the `Hasher`, the pool, the
batch APIs) and the SME2 hybrid kernel are tested, and unproved; so are
x86-64 and wasm32.

### How to read what is proved

**BLAKE3, as the proofs mean it.** `c2sp/BLAKE3/Blake3.lean` defines
BLAKE3 in Lean, as C2SP's standard states it. It follows `BLAKE3.md`
section by section, each definition under the standard's own text. It
mentions no implementation, so the proofs compare the kernels with the
standard itself. Its compression function (sections 2.2 to 3.3) is
generated from the standard's pseudocode, one rule per construct;
`check.py` confirms the generated text and reproduces every value in the
standard's appendix and the official test vectors.

| Part | Statement | Checked by |
|---|---|---|
| The proofs' definition of the compression is the standard's | `tools/verify/lean/Sound.lean`: `symbolic_is_the_specifications` | Lean |
| Each kernel computes that definition | `tools/verify/prove_hybrid.py`, `prove_sme2.py`: every output word equal to the definition's, which `lean_spec.py` reads from Lean's `compress.json` | Z3 |

**What the proofs take on trust.** Lean rests on its kernel and three
standard axioms (`propext`, `Classical.choice`, `Quot.sound`). The kernel
proofs prove the assembled machine code, and rest on Z3, on our model of
each AArch64 instruction they meet, on the assembler and disassembler,
and on `lean_spec.py`'s reading of Lean's `compress.json`. Each
instruction's model is checked against the CPU on random states and, for
322 of the 325 NEON and integer forms and 19 of the 23 streaming forms,
proved equal to Arm's own specification of the architecture (Sail's
Armv9.4, run by Isla); the rest, and the matrix unit's loads and stores,
are checked against the CPU.

**How the checkers are checked.**

- **The definition against the standard.** `check.py` regenerates the
  compression function from the standard's pseudocode and reproduces
  every value in its appendix and the official test vectors; Lean proves
  the definition the Z3 proofs read equal to it (`Sound.lean`).
- **The instruction models against the CPU and against Arm.**
  `cross_check.py` and `cross_check_sme.py` run every register form the
  kernels use on the CPU from random states and compare each result with
  the model; `isla_check.py` proves the forms equal to Arm's own
  specification, and shows that planted errors in a model are caught.
  Reviewing the models found one wrong flag (an addition's carry when one
  operand is 0), now modelled as Arm defines it.
- **The proofs against wrong code.** `mutants.py` plants errors in the
  kernels (a rotation off by one, a wrong operation, a schedule entry
  read from the next byte, a loop's wrong counter or pointer step), and
  each is rejected; a planted `sorry` fails the Lean checks.

### How to run the proofs and read their verdicts

Lean (install with [elan](https://github.com/leanprover/elan); each
directory's `lean-toolchain` names the version):

```sh
python3 c2sp/BLAKE3/check.py        # the definition: C2SP's text, its appendix, the test vectors
pypy3 tools/verify/lean/emit.py   # the proofs' compression is the standard's (needs python3-z3)
```

Each prints, for every theorem, the axioms it depends on, and fails on
any beyond Lean's standard three, so exit status 0 means Lean has checked
every proof it builds, completely.

Z3 (an AArch64 Linux machine with PyPy and `python3-z3`, Clang and
llvm-objdump 17 or later; details in [`tools/verify/README.md`](tools/verify/README.md)):

```sh
pypy3 tools/verify/prove_hybrid.py   # ends "327 of 327 cases proved"
pypy3 tools/verify/prove_sme2.py     # ends "36 of 36 cases proved" (hours: the chunk kernel at every group count)
pypy3 tools/verify/prove_sme2.py xof_every messages_every  # the other kernels at every group count (hours)
pypy3 tools/verify/mutants.py        # wrong kernels, each rejected
```

All of them run on the fork's VM before each promotion that changes a
kernel or the proof tools (`tools/verify/long-proofs.sh`), reported on
GitHub as the commit's status "long proofs". Each case is proved when Z3
finds no input on which the code and the definition differ; one that
fails prints `NOT PROVED` with what it could not prove, and the run ends
with exit status 1.

## Check it yourself

On an Apple Silicon Mac, or on Linux with a C compiler that assembles
SME2 (clang 17 or later; set `CC=clang-19` or similar):

```sh
git clone -b servil https://github.com/johnservil/BLAKE3 && cd BLAKE3
cargo test --release --lib                        # 92 tests
cargo test --release --lib --features no_sme2     # 87
cargo test --release --lib --features pure        # 74
cargo test --release --doc                        # 22
cargo test --release --manifest-path test_vectors/Cargo.toml
```

The sanitizers and Miri need nightly Rust
(`rustup toolchain install nightly --component miri,rust-src,llvm-tools`):

```sh
RUSTFLAGS="-Zsanitizer=address" cargo +nightly test -Zbuild-std --target aarch64-unknown-linux-gnu --release --lib
RUSTFLAGS="-Zsanitizer=thread" cargo +nightly test -Zbuild-std --target aarch64-unknown-linux-gnu --release --lib
MIRIFLAGS="-Zmiri-num-cpus=4 -Zmiri-ignore-leaks" cargo +nightly miri test --features pure --lib -- unsafe_paths miri
```

(On macOS, use the target `aarch64-apple-darwin`.)

Timing claims are checked the same way: [bench-hashes](https://github.com/johnservil/bench-hashes)
measures the fork against the official crate and others on your machine.

## The bugs these steps found

Seven, all fixed; none reached the results of a documented function.
Three could have given wrong digests (1, 2, and 6); none is known to have
reached a user. Tests, coverage, review, CI, and Miri found them. The
proofs have found none in the implementation: what they found were faults
in the checking itself (an addition's carry flag modelled wrongly in the
executor, the machine-code proofs run on a build without the standard
library, and two translation bugs in Sail, reported upstream), each
fixed. Their contribution is the other half: for every input, the proved
parts compute the standard's BLAKE3. Each entry
names the commit that introduced the code and the one that fixed it, in
[github.com/johnservil/BLAKE3](https://github.com/johnservil/BLAKE3).

1. **The SME2 message kernel mishandled one-block messages**
   (`c/blake3_sme2_aarch64.S`, `blake3_sme2_hash16_messages_512`). Given
   messages of a single block, it compressed a first block, then ran the
   same block again as the last one, and left out the chunk-start flag
   on it. The digests would have been wrong. It came with the kernel
   (220de01), whose callers then passed only messages of two or more
   blocks. The tests of the first caller with one-block messages (the
   side-by-side chunk path) caught it before that path landed. Fixed in
   03ffc95: a one-block message now starts and ends on its last block.
2. **`Platform::hash_many` dropped the tail of an input that was not
   whole blocks** (`src/platform.rs`). This hidden, unstable function
   takes a message length as a type parameter. A length that was not a
   multiple of 64 bytes lost its last partial block with no error, so two
   messages that differed only in those bytes got the same digest. The
   fork inherited this from the official crate, where it persists in
   release builds; the fork's own callers always pass whole blocks.
   Coverage-driven tests found it; fixed in d395f9e: such a length is now
   a compile-time error. We reported it upstream
   ([BLAKE3-team/BLAKE3#590](https://github.com/BLAKE3-team/BLAKE3/issues/590),
   with a fix in [#591](https://github.com/BLAKE3-team/BLAKE3/pull/591)),
   together with a catalog of the public projects that call the function:
   each of them passes whole blocks.
3. **A batch path asserted on a CPU combination that does not exist**
   (`src/many.rs`, `hash_blocks`). It decided whether to use the padded
   SME2 group from the length of its pointer table. On SME2 without the
   SHA-3 extension, the fallback's spare lane made that length look like
   a padded group, and an assertion stopped the program. Every real CPU
   with SME2 also has SHA-3, so the case could not arise. Introduced in
   1ca0b1d, found by a new test of the fallback arrangement on SME2, and
   fixed in d395f9e: the function now records its own choice.
4. **A `Stream` branch would have hashed only the last buffer**
   (`src/stream.rs`, `finalize_handed_over`). After the stream had
   handed buffers to its hashing thread, `finalize` had a branch for "no
   hashing thread", which would have hashed the final buffer alone. That
   state cannot occur once a buffer has been handed over. Introduced in
   59ad5c1, found by coverage; fixed in d395f9e: the branch is now a
   fail-stop `expect`.

5. **On macOS a queue could allocate after warm-up** (`src/lanes.rs`).
   The queue promises no allocation once a program cycling its buffers
   has warmed it up. Apple's builds of the standard library allocate a
   `Mutex` or `Condvar` at its first use, and the pool's threads first
   slept, using theirs, only after `initialize_multithreaded` returned:
   CI's macOS run of the allocation test counted one allocation, and a
   probe with a backtrace per allocation named the SME2 thread's first
   sleep (64 and 48 bytes). Fixed in f75e6a6: the pool makes every one
   of them while it starts.

6. **`update_reader` could lose bytes before an error** (`src/io.rs`,
   `copy_wide`). Reading through a larger buffer (a39fb7c), it returned a
   reader's error before hashing the bytes already in its buffer, which
   the reader had consumed; a caller that retries after `WouldBlock`
   would have got a wrong digest without any sign. Found on review of
   the change, about 20 minutes after it reached servil, and fixed in
   5739af6: the bytes read are hashed first. A test with a failing reader
   and a retrying caller fails on a39fb7c and passes now.

7. **A data race in the queue's chain, by Rust's aliasing rules**
   (`src/queue.rs`, `State::link`). To link a new entry, the submitter
   made a reference to the whole last slot to store its atomic `next`,
   while the delivery thread could be taking that slot's buffer, a plain
   field; and it held the new slot as `&mut` while the delivery thread
   could already read it. No test saw a wrong digest (the compiled code
   touched only the atomic), but both are undefined behaviour: the
   compiler may assume such a reference is not raced. Miri found it in
   CI, running the queue's allocation test; since 0c928f9 only the field
   is touched, through the raw pointer, and a queue test small enough
   for Miri (`test_miri_queue_round_trips`) runs in CI's Miri step,
   failing on the old code under every seed tried.

## What each check would catch

| Check | Catches | Evidence | Cannot see |
|---|---|---|---|
| Machine-code proofs of the kernels | any wrong result for any input; a read or write outside the kernel's buffers; a broken calling convention; a path that depends on data | planted errors (a rotation off by one, an add made an xor, a read past a buffer, a loop's wrong step) are each rejected (`mutants.py`) | a fault in the instruction models (the CPU and Arm checks below cover it), or in the CPU itself (the self-test covers it) |
| Instruction models against the CPU and Arm's specification | a wrong model of an instruction the proofs rely on | the CPU check found the carry-flag error; Isla rejects planted model errors | loads, branches, and calls by contract, which the executor's run of the official vectors checks |
| Test vectors and the reference implementation | any wrong digest at the lengths and shapes tested, on any platform | found bugs 1 and 2 below | untested lengths and shapes |
| Startup self-test | a miscompiled, mislinked, or faulty-hardware kernel on the user's machine | its inputs run every kernel entry point (a unit test checks it each run), and each case's output feeds the next, so one wrong result changes every later one | faults that appear only after startup |
| Sanitizers, Miri, guard pages | out-of-bounds access, use after free, data races, undefined behaviour in the paths tested | Miri found bug 7; controls with planted faults are caught | paths not exercised |

## Formal verification: what we tried and considered

- **Kani** (bounded model checking) and **Aeneas** (safe Rust
  translated to Lean): used for the pool's cuts and batch tables (Kani)
  and the tree walk and the Hasher (Aeneas, with machine-code proofs of
  whole calls beside them), then set aside on October 16, 2026: they
  took most of the proofs' hours and tools, and mutation testing,
  coverage, and Miri test that Rust well. The proofs keep to the
  assembly, where tests reach least.
- **Miri**: used (above). It checks the executions it runs, which falls
  short of a proof, and it cannot run assembly or intrinsics.
- **Verus, Prusti, Creusot**: considered, not tried. They could
  prove the pool and the batch paths for every thread interleaving; the
  cost is annotating or restructuring the code (atomics, raw pointers,
  uninitialised memory).
- **hax to F\* or Rocq** (as used for libcrux): considered, not tried
  yet. It suits proving the portable Rust equal to BLAKE3's
  specification. That code is upstream's and the least changed.
- **SAW with a Cryptol specification**: considered, not tried yet. It
  proves C or LLVM code equal to a specification, and could cover the C
  NEON kernel. It does not model SME2.
- **Symbolic execution of the hybrid assembly**: done (above), with our
  own instruction models, proved equal to Arm's specification through
  Isla.
- **The SME2 assembly**: done (above), with our own models of the
  streaming and ZA instructions, proved equal to Arm's specification
  where Isla can run them and checked against the CPU elsewhere.
- **Constant-time behaviour**: see "Timing and secrets", below.
- **Fuzzing (cargo-fuzz)**: not used. The tests enumerate every kernel
  at every input shape, count, and boundary against fixed answers, the
  paths a fuzzer would search for.

## Timing and secrets

If you hash a secret, or a message that contains one, can the time the
hash takes reveal anything about it? Three conditions decide it. When
all three hold, the time depends only on the message's length: whoever
chooses the other bytes, wherever the secret's bits sit among them, and
however often the hash is timed.

1. **The instructions run, and the memory addresses they touch, depend
   only on the length.** Proved for every AArch64 assembly kernel but the
   SME2 hybrid kernel, as assembled: each proof stops at any branch,
   memory address, or table index that depends on the key or the message.
   The Rust code around the kernels is written to branch on lengths
   alone; no proof checks it.
2. **Each instruction takes the same time whatever values it computes
   on.** That is a promise of the CPU. Arm CPUs make it, for a listed set
   of instructions, while data-independent timing (DIT) is enabled. The
   fork does not enable DIT; its cost is still to be measured.
3. **Power does not show in the timing.** A chip's power draw depends
   on the data it computes, and power can change its clock speed and so
   the time (the Hertzbleed attack, 2022). A fixed clock speed removes
   this channel; no proof about code reaches it. Apple M1 to M3 chips
   also have a prefetcher whose behaviour depends on the data in memory
   (the GoFetch attack, 2024); Apple's guidance for cryptographic code
   is to enable DIT.

## Not yet done

No person has reviewed the code line by line, and nobody has audited it.
The test suites have run on an Apple M4 Max, under macOS and in a
Debian 12 AArch64 VM on it (whose SME2 unit the VM exposes), and on
CI's hosted machines; the sanitizers on both, Miri in the VM.
